Analysts were waiting for compute to start and pipelines to finish during live decision-making. I owned the implementation of a Polars-based runtime, matching the execution model to the workload.

From ~20 minutes to under a minute.A faster feedback loop, with stage-level telemetry to verify the improvement.
PolarsAzureDatabricksObservability
Inside the project +

The problem

Unscheduled analytics sessions made cluster start-up latency visible to the business. Keeping distributed compute warm also carried a cost.

My contribution

I implemented the runtime and guided instrumentation and validation across workloads. The initial Polars recommendation came from a colleague; I owned turning it into a working solution.

The engineering judgement

Use single-node compute where the workload fits; retain distributed processing where volume justifies it. Keep outputs available through the existing data platform.

The evidence

Stage timing, CPU usage and workflow telemetry supported the before-and-after comparison. This result describes the measured workflow, rather than a universal performance claim.

The problem

Teams needed discoverable data and common delivery patterns, without rebuilding access controls, orchestration and quality checks for each product.

My contribution

I was the initial engineering lead for the catalogue, covering infrastructure, services, stakeholder work and delivery. I also extended an existing shared framework with pipeline stages, secure adapters, runtime templates and operational patterns.

What changed

The catalogue became a maintained product with a wider team. Shared capabilities gave engineers tested components for data access, quality checks, retries, audit metadata and health alerts.

The engineering judgement

Standardise the repeated work while keeping domain rules in the individual data product. A successful platform includes adoption and a usable handover.

The problem

An agent can generate code quickly, but incomplete context and hidden assumptions can make the result difficult to trust.

My contribution

I led the experimentation and shaped the delivery framework around stage-level mapping contracts, planning gates, test-first implementation and evaluation of bounded tasks.

The controls

Surface assumptions for human review. Restrict data access through permissions. Use controlled execution environments and evaluate whether the implementation satisfies its contract.

Where it stands

This is prototype and hackathon work. It demonstrates an engineering approach; it is not presented as an independently verified production rollout or a guaranteed delivery-time reduction.

FROM CAPABILITY TO CONTROL Explore the decisions ↓

01

Connect to useful capabilities.

Give agents access to the APIs, data and tools that solve a real problem. Keep each tool narrow enough to understand, test and authorise.

A connection is a capability. Access is a decision.
02

Ground answers in your reality.

Bring schemas, trusted data and domain rules into the system. Preserve the source and context so people can trace an answer back to its evidence.

Good context makes an answer useful. Evidence makes it reviewable.
03

Make uncertainty visible.

Define the outcome before asking an agent to work. Make assumptions explicit, evaluate the result and involve a person when the system lacks enough information.

An honest question is more useful than a confident guess.
04

Keep the work bounded.

Split complex workflows into clear tasks with explicit inputs and outputs. Use deterministic code for calculations and execution, with retries and observable state.

Every step needs a contract, an owner and a way to recover.
05

Enforce the boundary.

Carry identity through every call. Apply least privilege, authorise the action and resource, and retain the evidence needed to explain what happened.

Permission belongs in the system, beyond the prompt.
